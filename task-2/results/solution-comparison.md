# Task 2. Выбор технологического решения для генерации B2B-прайс-листов

## Исходные условия

- Запуск строго по расписанию: ежедневно в 06:00.
- Объём: 5 000–10 000 результирующих строк.
- Источники: `products` 5–10 тыс., `categories` 50–200, `clients` 100–500, `client_prices` 10–20 тыс. строк.
- Дополнительная сложная обработка не требуется: нужно связать данные и выгрузить CSV/XLS.
- Инфраструктура — облачные микросервисы.

## Сравнение решений

| Критерий | Spring Batch | Apache Airflow | K8s Job/CronJob | Spark |
|---|---|---|---|---|
| Наличие конфигурации CRON-расписания | Нет встроенного планировщика; нужен внешний scheduler, Kubernetes CronJob или Quartz | Да, полноценный scheduler с календарными расписаниями и backfill | Да, нативное `schedule` в CronJob, включая `timeZone` | Нет, нужен внешний оркестратор |
| Сложность реализации логики по обработке данных | Средняя: требуется Java-приложение, job/step/item reader/writer; оправдано при сложной chunk-обработке | Средняя/низкая для Python DAG, но нужно поддерживать Airflow | Низкая: один SQL/скрипт/контейнер, запускаемый по расписанию | Высокая для текущей задачи: нужен Spark job и кластер/рантайм |
| Ресурсоёмкость решения | Средняя: постоянная или запускаемая JVM, БД метаданных Spring Batch | Высокая: scheduler, webserver, worker, metadata DB | Низкая: контейнер запускается только на время выгрузки | Очень высокая: driver/executors, память и кластерные ресурсы |
| Масштабируемость под нагрузкой и сложность реализации | Хорошая внутри JVM/chunk processing, но горизонтальное масштабирование нужно проектировать | Хорошая для множества пайплайнов, но избыточна для одного ежедневного экспорта | Достаточная для данной задачи: parallelism не нужен, масштабирование через разбиение по клиентам возможно отдельными Job | Отличная, но не нужна при 10 тыс. строк |
| Сложность развёртывания в облаке и интеграция с микросервисной архитектурой | Средняя: нужен сервис, CI/CD, конфигурация, job repository | Средняя/высокая: отдельная платформа оркестрации | Низкая: стандартный Kubernetes manifest рядом с микросервисами | Высокая: нужно поддерживать Spark runtime |
| Удобство интеграции с системами логирования и мониторинга | Хорошее: Java metrics/logging, но нужно настраивать | Очень хорошее: UI, метрики, логи задач, alerting | Хорошее: stdout в централизованные логи, метрики Job/Pod, alerts на failed Job | Хорошее при наличии Spark monitoring, но сложнее |

## Вывод и выбор

Для описанного сценария оптимальным является **Kubernetes CronJob с контейнеризированным exporter-модулем**.

Причины:

1. Объём мал: 5–10 тыс. строк не требуют Spark или сложного chunk processing.
2. Логика простая: join таблиц и сериализация результата в CSV/XLSX.
3. Расписание нативно поддерживается Kubernetes.
4. Ресурсы потребляются только во время выполнения выгрузки.
5. Решение естественно вписывается в облачную микросервисную архитектуру и не требует отдельной платформы оркестрации.
6. Операционная модель простая: образ в registry, CronJob manifest, ConfigMap/Secret, объектное хранилище для результата, стандартные логи и alerts.

**Spring Batch** стоит рассматривать, если появятся сложная построчная валидация, restartability на уровне chunk, компенсации и массовая параллельная обработка внутри одной JVM. **Airflow** будет оправдан, если количество взаимосвязанных пайплайнов вырастет и потребуется централизованный оркестратор. **Spark** для текущего объёма является избыточным.

## Предлагаемое поведение To Be

1. Kubernetes CronJob ежедневно в 06:00 создаёт Job.
2. Job запускает контейнер `price-list-exporter`.
3. Exporter читает конфигурацию и параметры подключения из ConfigMap/Secret.
4. Выполняется потоковый SQL-запрос, соединяющий `products`, `categories`, `clients`, `client_prices`.
5. Для каждого B2B-клиента формируется CSV/XLSX-файл во временный каталог.
6. Файлы загружаются в объектное хранилище или передаются в сервис доставки.
7. В логи и метрики записываются длительность, количество строк, количество файлов, ошибки БД/хранилища.
8. При ошибке Kubernetes выполняет retry по `backoffLimit`; повторные запуски не создают параллельных дублей благодаря `concurrencyPolicy: Forbid`.
9. После успешной выгрузки внешняя система уведомляет клиентов или предоставляет файлы через портал.
