# ADR-001. Использование Spring Batch для ETL обработки складских отчётов

## Статус

Accepted for transition architecture.

## Контекст

TradeWare обрабатывает CSV-отчеты складов синхронно внутри Java/WildFly монолита. В пиковые периоды поступает до 400 000 строк в сутки, а нагрузка может возрастать в 2–3 раза. Обновления выполняются построчно, отчётность и онлайн-операции конкурируют за ресурсы, интерфейс блокируется, ошибки сложно диагностировать. Компания уже перенесла БД в GCP и файлы в Google Cloud Storage, но batch processing как отдельный архитектурный компонент отсутствует.

Требования:

- обработка отчёта на 2 000 строк в среднем до 30 секунд;
- 100–150 параллельных загрузок в пике;
- масштабирование под сезонную нагрузку;
- валидация, обогащение справочными данными, пакетная запись;
- retry/restart, quarantine для некорректных данных;
- интеграция с Java-экосистемой и PostgreSQL;
- возможность постепенно выносить функциональность из монолита.

## Решение

Ввести выделенный **Inventory Batch Processing Service** на базе **Spring Batch**.

### Целевой поток

1. Пользователь загружает CSV через ERP UI.
2. Монолит выполняет только быструю первичную проверку: доступность файла, базовый размер, тип, обязательные HTTP-параметры.
3. Файл сохраняется в GCS в `raw/` prefix.
4. Монолит регистрирует задание в таблице `ingestion_job` или публикует событие в очередь.
5. Пользователь сразу получает `job_id` и статус `ACCEPTED`; ожидание полной обработки в HTTP-запросе устраняется.
6. Один из масштабируемых Spring Batch workerов забирает задание.
7. Spring Batch job выполняет шаги:
   - `validateFileStep` — структура CSV, обязательные колонки, кодировка, контрольные размеры;
   - `validateAndEnrichChunkStep` — построчная валидация, нормализация, обогащение справочниками, разделение valid/invalid rows;
   - `loadStagingStep` — batch insert валидных строк в staging table;
   - `mergeInventoryStep` — set-based merge/update результирующих таблиц остатков;
   - `finalizeStep` — фиксация статистики, статуса, ссылки на отчёт об ошибках.
8. Невалидные строки сохраняются в `quarantine/` в GCS и/или в таблице ошибок с номером строки и причиной.
9. Пользователь видит статус обработки и получает уведомление о результате.

### Технические решения

- Spring Batch Job Repository — в PostgreSQL.
- Чтение CSV — потоковое, без загрузки всего файла в память.
- Запись в staging — чанками, например 500–2 000 строк, размер настраивается.
- Обновление результирующих таблиц — set-based SQL merge после staging, чтобы не выполнять построчные update в operational DB.
- Идемпотентность — по `file_hash`, `job_id`, версии схемы и уникальным бизнес-ключам; повторная обработка не создаёт дубли.
- Retry — на уровне chunk/step для transient ошибок инфраструктуры; бизнес-ошибки не retry, а отправляются в quarantine.
- Restartability — используется встроенная модель Spring Batch ExecutionContext/JobRepository.
- Параллельность — горизонтальное масштабирование workerов; распределение заданий через очередь или SELECT FOR UPDATE SKIP LOCKED.
- Деплой — контейнер в GKE/Cloud Run Jobs; периодические/системные запуски через Cloud Scheduler или Kubernetes CronJob, событийные запуски — через очередь.

## Почему Spring Batch подходит

1. **Совместимость с командой и стеком**: Java 11, Spring, JDBC, PostgreSQL уже используются, инжиниринг-лид имеет опыт Spring Batch.
2. **Chunk-oriented processing**: подходит для CSV → validate/enrich → write.
3. **Retry/skip/restart**: встроенные механизмы соответствуют требованиям надёжности.
4. **Транзакционная предсказуемость**: чанки фиксируются контролируемо, ошибки локализуются.
5. **Постепенная миграция**: сервис можно развернуть рядом с монолитом без переписывания всего ERP.
6. **Наблюдаемость**: Micrometer интегрируется с Prometheus, structured logging — с централизованным сбором логов.

## Рассмотренные альтернативы

| Вариант | Плюсы | Минусы | Решение |
|---|---|---|---|
| **Apache Airflow / Cloud Composer** | Сильная оркестрация DAG, UI, retry, интеграции | Избыточен для обработки пользовательских загрузок в near-real-time; требует отдельной платформы; обработка всё равно должна быть в workerах | Не выбран как основной обработчик; может использоваться позже для ночных аналитических pipeline |
| **Apache Spark / Dataflow** | Высокая масштабируемость, параллельная обработка больших объёмов | Сложность и стоимость выше; текущий объём 400k строк/сутки не требует распределённого compute; команда Java/ERP не специализируется на data engineering | Не выбран сейчас; рассмотреть при росте объёмов на порядки |
| **Kafka Streams / event-driven consumers** | Хорошая горизонтальная масштабируемость, backpressure | Требует внедрения Kafka и перестройки интеграций; CSV batch semantics менее естественны | Не выбран как первый шаг; можно добавить очередь как транспорт заданий |
| **Kubernetes CronJob + простой скрипт** | Просто для регулярных выгрузок | Не подходит для event-driven пользовательских загрузок, restartability и сложной построчной диагностики | Не выбран как основное решение; CronJob может запускать служебные job |
| **Оставить обработку в монолите** | Минимум изменений | Сохраняет блокировки, построчные update, отсутствие масштабирования | Отклонено |

## Последствия

### Положительные

- ERP UI перестаёт ждать завершения обработки файла.
- Построчные update заменяются на batch staging + set-based merge.
- Batch workerы масштабируются независимо от monolith.
- Появляется единый lifecycle задания и аудит ошибок.
- Retry/restart становятся управляемыми и наблюдаемыми.
- Решение создаёт первый выделенный сервис для дальнейшей миграции к микросервисам.

### Отрицательные/риски

- Spring Batch не является полноценным внешним оркестратором: нужна модель распределения заданий и deployment automation.
- Требуется аккуратно спроектировать идемпотентность и блокировки, чтобы не было параллельной обработки одного файла.
- Job Repository в PostgreSQL добавляет нагрузку; нужно мониторить и выделять ресурсы.
- При большом росте объёмов может потребоваться переход к Dataflow/Spark для аналитической части.

## Меры снижения рисков

1. Ввести таблицу `ingestion_job` со статусами `ACCEPTED/RUNNING/SUCCEEDED/FAILED/QUARANTINED` и уникальным `file_hash + business_date + warehouse_id` там, где это применимо.
2. Использовать `SELECT ... FOR UPDATE SKIP LOCKED` или очередь для распределения заданий между workerами.
3. Ограничить concurrency на уровне пула workerов и connection pool PostgreSQL.
4. Настроить alerts на backlog, failed jobs, длительность и retry count.
5. Провести нагрузочный тест: 2 000 строк ≤ 30 секунд; 100–150 одновременных файлов.
6. Начать с одного типа отчёта, затем распространять на другие источники.

## Дорожная карта внедрения

1. Спроектировать схему таблиц `ingestion_job`, `ingestion_job_error`, staging tables.
2. Реализовать Spring Batch service и Docker-образ.
3. Добавить в монолит быструю регистрацию задания и загрузку файла в GCS без ожидания обработки.
4. Развернуть worker в GCP/GKE/Cloud Run Jobs.
5. Настроить масштабирование, structured logs, Micrometer/Prometheus metrics.
6. Реализовать UI/API статуса и уведомления.
7. Провести нагрузочное тестирование и tuning chunk size/connection pool.
8. Постепенно отключить синхронную обработку в монолите.
